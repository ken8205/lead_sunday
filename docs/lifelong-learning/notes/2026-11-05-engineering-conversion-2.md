# 공학 트랙 — 공학적 사고 입문, 세션 2/3 (+ 실질적으로 세션 3 포함)

- **일자**: 2026-11-05 (세션 1의 전환율 문제, 2026-10-28에서 이어짐)
- **트랙**: 공학 (`engineering-tutor`)
- **주제**: 측정 설계와 트레이드오프 분석
- **진행**: 3회 중 2회 — 실제 적용(3회차 목표)까지 함께 다룸

## 배경

세션 1에서 정식화한 문제: 상담문의→매출 **전환율**을 높이되, 수가는 낮추지 않고 과장광고도 하지 않는다. 후보안 셋: 콘텐츠 발행, 상담방식 개선, 비용전달방식 개선.

## 뜻밖의 전개 — 이미 만들어진 실제 시스템 발견

원장님이 지난 몇 주간 별도 Claude Code 세션에서 **`inquiry-stats`**(상담 통계 앱, React+Vite+Supabase, 이 저장소의 `main` 브랜치에 배포됨)를 이미 구축해 운영 중이었다. 몇 주 전 과학 세션(베이컨)에서 그렸던 "1단계: 엑셀 기록 → 2단계: 패턴 확인 → 3단계: 코드화"의 3단계가 사실상 이미 실현되어 있었다.

**기존 스키마 확인**: `stats_entries`(entry_date, kind, source, channel, interest, amount 등)로 문의·상담·시술을 날짜별·경로별로 이미 추적 중. 광고비·수수료 기반 마케팅비 계산, 에이전시 경로 분리, 개인정보 비식별화 원칙까지 이미 반영되어 있었음.

## 핵심 개념 — 측정 설계의 트레이드오프

후보안의 효과를 검증하려면 "이 상담이 새 방식이었는가"를 구분할 방법이 필요하다는 데까지 원장님이 스스로 도달. 두 설계안을 비교:

1. **카드마다 태그 추가** — 정확하지만 매 입력마다 부담 증가, 누락 위험
2. **개입 시작일만 별도 기록** — 스키마 변경 없이 기존 `entry_date`로 전/후 비교 가능, 대신 다른 시기 요인과 섞일 위험

## 공학적 판단 (오늘의 결론)

세 후보 모두 **특정 날짜부터 전체 상담에 일괄 적용**되는 방식(일부 환자만 골라 동시에 비교하는 A/B 테스트가 아님)이므로, 태그 없이 **개입 시작일만 기록하는 쪽으로 결정**. 이것이 공학적으로 올바른 이유: 추가 복잡성(매 카드 태그)이 주는 정보가, 이미 날짜 필드로 얻을 수 있는 정보와 중복되기 때문 — 최소 복잡성 원칙. (단, 향후 일부 환자군에만 새 방식을 먼저 시도하는 실험을 하게 되면 태그가 다시 필요해짐 — 그 경우만 예외.)
